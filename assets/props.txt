# The prop catalogue.
#
# Everything the engine needs to know about a kind of entity that is not a
# player, in a file both the server and the client read. Adding a prop is
# editing this file and naming it from a map's Lua -- no C++, no JavaScript, and
# nothing to recompile on either side.
#
# TWO RECORD TYPES, because two different programs need two different halves and
# neither should have to understand the other's:
#
#   prop   <id> <name> radius <r> height <h> [speed <s>] [scale <k>] [solid] [usable]
#           The SIMULATION's half. The server reads it. `radius` and `height`
#           are the cylinder an agent has to be inside to touch the thing;
#           `solid` means a body cannot walk through it, and `usable` means
#           pressing use while facing it is reported to the script. `speed` is
#           world units per second for anything that walks, and becomes the
#           entity's move_speed -- a replicated parameter, so a slow monster is
#           slow on every client without a word of it crossing the wire. Absent
#           means the engine's default.
#
#           A prop with neither flag is a trigger volume you walk into -- a key,
#           a checkpoint. With `solid` it is an obstacle. With `usable` it is
#           something you press. They compose: a lever on a plinth is both.
#
#           `scale` is the exception on this line and the server reads past it:
#           it multiplies how big the kind is DRAWN, over whatever its picture
#           would otherwise be -- the `size` on a sprite line, or the height the
#           sheet declares for an atlas. It is here rather than on a visual line
#           because it is a fact about the KIND: a big imp is big in every state
#           and from every angle. And it is a MULTIPLIER rather than a size, so
#           it is not a second opinion about a number the sheet already carries
#           -- which is what the atlas line refuses to restate.
#
#           It does not touch the body. A scaled-up prop is exactly as wide and
#           as tall to walk into as it was, because that half is replicated and
#           predicted: drawing one size and colliding at another is a
#           misprediction on every touch and looks like a netcode fault.
#
#
#   sprite <id> size <world-height> [billboard] [rot8] [once] [state <n>] [fps <f>]
#                                   [blend <seconds>] frames A,B,C
#   mesh   <id> model <name> [state <n>] [clip <name>]
#   avatar <id> [blend <seconds>]
#   avatar <id> when <condition> state <n>
#           WHICH RECORD DRAWS A PLAYER is the `avatar` line, and it is a line
#           rather than a record because a player is kind 0 on the wire and kind
#           0 is structurally "no prop" in both readers. That cannot change: an
#           agent's kind is in the hash the client predicts against and is absent
#           from the block that would reconcile it, so a server that gave a
#           player its own kind would mispredict every tick forever. So the art
#           is an ordinary record and only its ADDRESSING is special.
#
#           `when <condition> state <n>` points one of the animation conditions
#           at a state this catalogue drew -- `when climb state 7`. Without it
#           the condition-to-state map would be numbers compiled into the client,
#           which is the one thing this file exists to prevent. The conditions
#           are the closed list in client/src/render/animstate.js; a name that is
#           not one is a warning. Every condition already has a default, so
#           `avatar <id>` alone works.
#
#           `blend <seconds>` cross-fades between states. ABSENT MEANS ZERO
#           means today's hard cut, byte for byte -- a dissolve between two
#           hand-drawn Doom frames is a double exposure that reads as a renderer
#           fault, which is why this is opt-in per record and the Doom catalogue
#           never opts in.
#
#           The RENDERER's half. The client reads it; the server never looks.
#           A kind may have several state lines, one per animation state, and
#           the server declares the STATE while the client owns the timing
#           (design §4) -- a sprite swaps frames on its own clock and a mesh
#           cross-fades on its own.
#
# Both parsers ignore records they do not understand, so a visual-only addition
# does not need the server restarted and a physics-only one does not need the
# assets rebuilt.
#
# `id` is explicit and never positional: two files that happened to list props
# in a different order would otherwise silently swap them.

# WHAT IS *NOT* IN THIS FILE, AND WHY.
#
# Every prop with a picture used to live here, and every one of those pictures
# came out of DOOM2.WAD -- the keys, the barrel, the lever, all eighteen
# monsters. That art is id Software's, and an engine whose default catalogue
# points at it cannot be handed to anybody, nor can a new project start from it
# without inheriting the problem.
#
# So the whole Doom catalogue moved to modules/doom2/assets/props.txt, next to
# the sprites and textures it names. Load it the way you load any module:
#
#     scripts/run_stack.sh --module doom2
#
# What stays here is what the engine itself authored. At present that is the
# transient effects below, which are colours and numbers and nothing else.
#
# This file is deliberately nearly empty. That is the point: it is the
# catalogue a project starts from, and it starts clean.

# --- transient effects -------------------------------------------------------
#
#   vfx <kind> tracer [colour <hex>] [width <w>] [life <seconds>]
#
# Fire and forget, off the entity path: a tracer has no identity and nothing
# refers to it. The engine reports "effect 1 happened here, pointing that way";
# what a 1 IS lives here, which is what makes it customisable without touching
# either binary.

# Wide enough and slow enough to actually SEE.
#
# These were 0.035 wide and lasted a tenth of a second, which at 1/48 Doom
# scale is a sub-pixel line for about six frames -- correct, drawn, and
# invisible, which is indistinguishable from broken and was reported as such
# three times. A tracer is not a simulation object: nothing collides with it and
# nothing depends on its size, so the only question it has to answer is whether
# a person can tell a shot was fired. These are the numbers to turn down if they
# turn out to be gaudy, and turning them down needs no recompile.
vfx 1 tracer colour ffee88 width 0.09 life 0.35
vfx 2 tracer colour ff8844 width 0.12 life 0.45

# --- particles ---------------------------------------------------------------
#
# Bursts, drawn entirely by the client from one event. Nothing crosses the wire
# but the kind number, the place and the direction: the server does not simulate
# a particle and none of them is in any hash.
#
# `cone` is in TURNS like every other angle in this engine -- 0 is a beam along
# the event's direction, 0.25 a hemisphere, 0.5 a full sphere -- and the event's
# `param` is the radius they come out of, so a blast can fill its own radius.
#
# ADDITIVE unless told otherwise, which is what makes the colour ramp double as
# the fade: black is invisible under additive blending, so one attribute does
# both and no shader is needed.
#
# ONE LINE EACH. There is no continuation character: a line not starting with a
# record keyword is skipped in silence, so a wrapped entry keeps the attributes
# before the break and loses every one after it. Which is a kind that looks
# configured, parses without a warning, and draws the defaults.

# A hit: a short spray, thrown back along the blow.
vfx 10 particles count 14 life 0.45 life_var 0.2 speed 7 speed_var 4 cone 0.18 gravity 22 drag 2 size 0.09 size_end 0.02 colour ff5533 colour_end 330000

# A rocket going off: fast, wide, and it falls.
vfx 11 particles count 40 life 0.8 life_var 0.4 speed 14 speed_var 8 cone 0.5 gravity 16 drag 1.2 size 0.16 size_end 0.02 colour ffdd88 colour_end 662200

# Sparks off a wall, tight and quick.
vfx 12 particles count 8 life 0.3 life_var 0.15 speed 9 speed_var 5 cone 0.3 gravity 30 drag 1 size 0.05 size_end 0 colour ffffcc colour_end 442200

# Smoke, and the one that is NOT additive: fading to black would be soot rather
# than absence, so the whole burst fades on the material instead.
vfx 13 particles count 10 life 1.6 life_var 0.6 speed 2 speed_var 1 cone 0.4 gravity -1 drag 2 size 0.2 size_end 0.6 colour 555555 colour_end 222222 blend alpha
